# 君君下一阶段优化计划（2026-07-30）

> 衔接《优化计划_2026-07-28》（W1/W2 已完成，W3 部分欠账）。
> 主题：**先升级「脑子」和「耳朵」，再谈「手脚」；给手脚之前先戴三层镣铐。**

---

## 〇、现状评估

君君已是完成度较高的单体 Agent：感知（消息/图片/表情/链接/引用）、
决策（LLM 工具循环 + 召回掩码 + 权限裁决）、行动（20+ 工具）、
记忆（短期摘要/长期记忆/知识库/关系）、自主性（定时日记/主动搭话/回评论/情绪）
五环俱全，且在真实生产环境稳定运行。

当前主要瓶颈（按对体验的影响排序）：

1. **单轮决策硬撑多步任务**——「搜一下 XX 再画个图发空间」靠模型一轮硬想，
   没有显式规划-执行-验证，复杂任务成功率不稳。
2. **语音仍是盲区**——收到语音只显示 `[语音]`，更谈不上语音对话。
3. **记忆/关系是「存了但用得浅」**——亲密度没有真正驱动行为差异。
4. **权限边界清晰但能力天花板低**——只能聊天和发内容，不能帮主人操作电脑
   （这是一个**需要谨慎打开**的口子，见 W7 威胁模型）。

原则：每项独立可交付、独立可回滚；高危项一律「只读先行、确认兜底、沙箱隔离」。

## W4 决策质量——先修「脑子」（性价比最高）

### P0-12 轻量规划循环（Plan-Execute）
- **现状**：复杂请求依赖 LLM 单轮内隐式规划，GLM 级模型经常半途忘步骤
  （搜完忘画图、画完忘发空间）。
- **方案**：processor 前置一个轻量「复杂度判定」（规则：多动词/多对象/含「然后」
  等触发词 → utils 槽 LLM 出 1 句话计划）。命中复杂任务时，在系统提示注入
  「执行清单」：把任务拆成有序步骤，Agent 每完成一步由框架在上下文里
  打勾（`[步骤 2/3 已完成: 搜索结果已获取]`），直到清单走完。
  **不引入 LangGraph 子图**（上轮论证 GLM function calling 稳定性撑不起），
  只用「清单注入 + 进度回填」这种模型无关的弱约束。
- **触点**：`junjun_agent/processor.py`（前置判定）、`persona/__init__.py`
  （清单注入）、新增 `junjun_agent/loop/plan_tracker.py`
- **验收**：「搜一下下周新番然后画张图发空间」类复合指令 10 次成功率 ≥ 8
  （现状目测 ≤ 5）。
- **工作量**：1.5 天 | **风险**：中（误触发浪费一轮 utils 调用，可用规则收紧）

### P0-13 工具失败结构化反馈 + 自主换乘
- **现状**：工具失败返回错误文案，部分场景模型直接放弃或降级，
  不知道「还能换别的工具」（如 web_search 失败可换 MCP tavily/fetch）。
- **方案**：工具错误统一为结构前缀 `[TOOL_ERROR kind=网络/参数/权限/限流]`，
  系统提示补充换乘规则表（搜索失败→备用搜索；画图失败→改提示词重试一次；
  权限不足→直接告知用户不要重试）。网络类错误框架层已 3 次重试，
  这层是给模型的「换乘地图」。
- **触点**：`junjun_skills/registry.py`（错误包装）、`persona`（规则注入）
- **验收**：人为断网/断 API 各 3 次，Agent 均给出合理换乘或明确告知，
  无「沉默」和「胡说」。
- **工作量**：1 天 | **风险**：低

### P0-14 感知就绪等待（治「决策太快」根因）
- **现状**：图片 VLM 预热已做，但仍是「到时没好就先用文字上下文决策」，
  偶发「看不到图片」。
- **方案**：决策前检查本轮消息的感知任务（图片/语音/视频描述）完成度，
  未就绪且预计等待 ≤3s 时**主动等一轮**（asyncio.wait_for 挂起决策），
  超时再降级。配合 P1-15 ASR 统一为「感知任务注册表」。
- **触点**：`junjun_agent/processor.py`、`junjun_memory/vision.py`
- **验收**：发图立刻提问 20 次，「没看到图」出现 0 次。
- **工作量**：0.5 天 | **风险**：低（上限等待时间可调）

## W5 语音对话——补上「耳朵和嘴」

> 背景结论（2026-07-30 已评估）：QQ 语音电话双向实时通话**协议层不可行**
> （OneBot 无语音通话 API，所有框架一样）。可行的是「语音消息对讲模式」
> （延迟 3~8s）和「网页实时通话」（1~2s，不经 QQ）。

### P1-15 ASR 接入（落地欠账 P2-10）
- **方案**：SiliconFlow FunAudioLLM/SenseVoiceSmall（免费额度）。
  adapter record 段保留 URL → 下载（silk）→ ffmpeg 转 wav → ASR →
  注入 `[语音: 明天一起开黑吗]`。复用 vision 的异步预热 + 注册表（P0-14）。
  ASR 失败降级 `[语音]`，不阻塞回复。
- **触点**：`junjun_adapter_napcat/recv_handler/message_handler.py`（record 段）、
  新增 `junjun_memory/asr.py`、`processor.py`
- **配置**：`.env` 加 `SILICONFLOW_API_KEY`；`[asr] enable / api_base / model / max_duration`
- **验收**：发 10 条 5~15s 语音，转写注入 ≥ 9 条，平均延迟 ≤ 4s。
- **工作量**：1 天 | **风险**：低

### P1-16 语音对话模式（对讲机）
- **方案**：私聊发「语音模式」开关（或检测到对方连续发语音自动提示开启）。
  开启后：语音 → ASR → Agent → 回复文本走 unified_tts 合成语音发回
  （TTS 已上线，16kHz 采样率已调优）。文字消息在语音模式下照常文字回。
  状态存 chat_state，超时 30 分钟无语音自动关闭。
- **触点**：`junjun_agent/processor.py`（回复路由）、`junjun_skills/builtin/`
  （模式切换命令）、`junjun_express/tts`
- **验收**：完整完成 5 轮「语音问→语音答」，端到端延迟中位 ≤ 8s。
- **工作量**：1 天 | **风险**：低 | **依赖**：P1-15

### P2-17 语音延迟优化（可选）
- **方案**：ASR 与决策流水并发（ASR 完成即决策，不等其他感知）；
  回复首句先合成先发，长回复分段发语音；TTS 短文本优先。
- **验收**：端到端中位延迟压到 ≤ 4s。
- **工作量**：1 天 | **风险**：低 | **依赖**：P1-16 上线后看数据再决定

### P3-18 网页实时通话（真·实时，独立大项）
- **方案**：本地 WebSocket 语音服务 + 手机浏览器页面：
  浏览器 VAD 收音（Web Audio API）→ 流式 ASR → Agent →
  流式 TTS 播放。延迟目标 1~2s。完全不依赖 QQ 协议，无封号风险。
- **触点**：新增 `junjun_voice_web/`（fastapi + websockets + 静态页）
- **验收**：手机浏览器连续对话 10 轮，延迟中位 ≤ 2s，断句自然。
- **工作量**：2.5~3 天 | **风险**：中（流式 ASR/TTS 成本与稳定性需实测）
- **建议时机**：W5 对讲模式用一段时间后，确认延迟不可接受再启动。

## W6 记忆与关系——让「存了的」真正用起来

### P2-19 关系驱动行为
- **现状**：关系系统（MCP 亲密度/惩罚）已能记分和查询，但只偶尔被工具调用，
  没有系统性地影响行为。
- **方案**：processor 每轮取当前用户关系值注入 `<state>`
  （亲密度档位：陌生/熟人/朋友/死党 + 近期互动摘要 1 句）；
  persona 层映射为行为差异：语气亲疏、开玩笑尺度、主动分享欲、
  语音/表情包使用倾向。proactive_chat 选人策略加入亲密度权重。
- **触点**：`junjun_agent/processor.py`、`persona/__init__.py`、
  `junjun_agent/loop/proactive.py`、relationship MCP（读接口）
- **验收**：对高/低亲密度两个测试账号，同一问题回复风格可区分
  （人工盲评）；主动搭话对象分布向高亲密度倾斜。
- **工作量**：1 天 | **风险**：低

### P2-20 LPMM 图记忆（观望→试点）
- **现状**：长期记忆是扁平条目 + embedding 检索，无关联结构。
  quick_algo 未装，PPR 跑不了。
- **方案**：先装 quick_algo 跑通最小链路：记忆条目间建「共现/同主题」边，
  recall 时 PPR 扩散取 top-k 相关簇，注入「相关联的记忆」。
  只读增强，不改写入路径，随时可回滚。
- **触点**：`junjun_memory/long_term.py`（检索增强层）
- **验收**：问「上次说的那个游戏」类指代问题，命中率人工评估有提升。
- **工作量**：1.5 天 | **风险**：中（依赖安装与调参）

## W7 电脑接管——「手脚」工程（高危，三层镣铐）

### 威胁模型（必读）

君君的输入面是**开放 QQ 群聊**——任何群友的一句话都是潜在指令。
现有安全体系（工具白名单、admin gate、越权上报）成立的前提是
**最坏情况只是发错消息**。一旦 Agent 能操作电脑，一条精心构造的群消息
（prompt injection）就可能变成：读文件发出去、删数据、替你转账。
**因此电脑控制默认对群聊和私聊全员不可见，仅管理员私聊 + 二次确认可用。**

### C0 安全基建（前置，没做完不开任何电脑工具）
- 高权限工具集独立注册表，仅在 `admin_privileged` 且**私聊**上下文注入；
  群聊/普通用户物理上看不到（不是提示词层面的"别用"，是工具不挂载）。
- 危险动作**二次确认**：Agent 描述动作 → 管理员回复「确认」才执行
  （5 分钟有效期，一次一确认）。
- 全量审计日志：动作/参数/确认人/结果落 `data/admin_actions.log`。
- 硬编码黑名单：删除类、转账/支付类、对外发送文件类、修改系统配置类
  永远拒绝，无确认通道。
- **工作量**：1 天 | **验收**：非管理员任何话术（含注入尝试）触发不到
  电脑工具；危险动作无确认不执行；日志完整。

### C1 只读感知（低风险先行）
- 截屏看屏幕（`mss` 截图 → VLM 描述，「我屏幕上现在是什么」）、
  读取指定目录文件列表/内容（限 `E:\JunJun_Agent` 与文档目录白名单）、
  系统状态（CPU/内存/电量/进程列表）。
- **工作量**：1 天 | **风险**：低（只读 + 目录白名单）| **依赖**：C0

### C2 受限写入（确认制）
- 在白名单目录内创建/修改文件（写代码、记笔记、改配置），
  每次写前diff预览 + 二次确认；启动白名单内的程序（如打开项目、启动脚本）。
- **工作量**：1.5 天 | **风险**：中 | **依赖**：C1 稳定 1 周以上

### C3 沙箱 computer use（终极形态）
- 虚拟机（VMware/Hyper-V）内跑 Windows/Linux，Agent 通过截图+键鼠
  接管**虚拟机**（宿主永不开放）。配浏览器和常用软件，
  「帮我在 XX 网站查个东西」「帮我挂个机」类任务。
- **工作量**：3~5 天 | **风险**：高（仅限沙箱）| **依赖**：C2 稳定 2 周以上

### W7 明确不做（红线）
- ❌ 宿主机直接键鼠接管
- ❌ 任何删除/支付/对外发送文件动作（硬编码禁止，无配置项）
- ❌ 电脑工具对群聊可见（无论任何话术）
- ❌ 记住/复述管理员密码、密钥类信息（检测到即拒绝并提醒）

## 横切保障

- **测试纪律**：每项新功能配 pytest（当前 639 例基线），高危项（W7）
  另配注入/越权攻击测试用例。
- **回滚**：每项独立配置开关（`enable`），出问题关开关即回滚；
  C 系每阶段独立分支合并。
- **成本**：ASR/TTS/VLM 调用量上升，接入前确认 SiliconFlow 额度
  与计费档位；语音模式默认仅私聊开启防刷。
- **欠账跟进**：音乐插件音源直连、maizone cookie 长期稳定性
  （看门狗已兜底，观察一个月）。

## 明确不做（本期）

- ❌ 多 Agent 架构（已论证，异步任务覆盖）
- ❌ 人脸识别/头像记忆（隐私风险高、收益低）
- ❌ 语音情绪识别（ROI 低）
- ❌ 宿主机直接 computer use（见 W7 红线）
